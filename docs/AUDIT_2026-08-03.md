# L2PTTRPG Product Audit

Audit date: 2026-08-03

Audited target: `main` at `2d57d6ffd2b7d43f835d6c8c8559949d17169385`

## Executive assessment

L2PTTRPG has a strong, coherent prototype foundation. It correctly exists as a separate product, deploys from `main`, provides six clearly labeled system choices, separates D&D editions, includes original player/GM orientation content, documents licensing boundaries, and refuses to enable unsafe community contact prematurely.

It is not yet the finished product originally described. The current release is best described as a polished orientation prototype. The largest gaps are content depth, crawlable SEO architecture, source-level editorial review, browser/accessibility testing, maintainability, and the real secure community backend.

## Highest-priority findings

### P0 — Truthful safety and compliance language

- Continue describing the community page as a prototype.
- Do not imply demo listings represent real verified users.
- Do not enable contact until #1 is complete.
- Do not claim ADA/WCAG compliance until #7 is complete.
- Do not present the licensing register as legal advice.

### P1 — Content depth

The original request calls for thorough teaching. The current model contains six player lessons and six GM lessons per system, generally with two or three bullets each. This is suitable as a landing overview, not as a complete learning curriculum.

The next content architecture should support dedicated sections/subpages, examples, first-session checklists, common mistakes, glossary terms, and system-appropriate creation guidance.

Tracked in #5.

### P1 — SEO and routing

All educational and blog content is rendered into one `index.html` through hash routes. Search engines and social previews receive one generic title, description, and schema record rather than unique page metadata.

Tracked in #6.

### P1 — Research and licensing evidence

The data records official source links and `lastReviewed`, but not source version, relevant rule section, reviewer, or review state. A future editor could change prose without knowing which source supports it.

Tracked in #8.

### P1 — Maintainability

Several important files are compressed into extremely long lines. Six systems are held in one data file, and most view rendering lives in one view file. This makes review, conflict resolution, citations, and future expansion harder than necessary.

Tracked in #10.

### P1 — Accessibility and browser QA

The semantic and CSS foundation is promising, but there is no automated accessibility scan, manual screen-reader/keyboard matrix, zoom test, contrast report, visual regression, route announcement, or public-site smoke test.

Tracked in #7.

### P2 — Visual identity refinement

The original SVG badge approach is correct. The actual badge direction needs one more design pass based on the latest decisions:

- D&D 2014: classic faceted d20.
- D&D 2024: distinct modern d20, not merely a generic spark.
- Pathfinder: visibly readable `3A` / three-action identity.
- Call of Cthulhu: original tentacled eldritch silhouette, not an official Chaosium mark.
- Daggerheart: original heart/duality identity.
- Vampire V5: clear original fangs and blood motif.

Tracked in #4.

### P2 — Blog and future systems

The blog records only simple date/title/dek/body paragraphs. Future growth needs structured article metadata, source/review status, richer content blocks, categories, related links, archives, and a controlled system-intake checklist.

Tracked in #9.

## Technical observations

### Strengths

- Static dependency-light codebase.
- No third-party image/font dependency in the badge system.
- Clear unofficial disclaimer.
- Defensive rendering and route parsing error handling.
- Route changes move focus to main content.
- Community data intentionally uses coarse location and no public direct contact.
- Deployment tests execute before Pages publication.

### Risks and improvements

- The root directory is uploaded as the Pages artifact instead of a deliberate build directory.
- There is no schema validator for system/article/listing records.
- There is no escaping/validation policy for every future content field; current records are trusted static data.
- Disabled community buttons explain that functionality is coming later, but future UX should clearly distinguish examples from real listings.
- Blog dates should use semantic `datetime` values and page-specific metadata.
- Navigation should expose active-page state and route-change announcements.
- External link behavior should receive a consistent accessibility review.
- Add changelog/versioning and document release rollback procedure.

## Decisions preserved from the conversation

1. The project repository is `cbw29512/L2PTTRPG`.
2. Dungeon Cards remains a separate product.
3. Production deployment comes from `main`.
4. Launch systems are D&D 2014, D&D 2024, Pathfinder 2E Remaster, Call of Cthulhu 7E, Daggerheart, and Vampire V5.
5. Additional systems will be added later through a controlled intake process.
6. Official logos are not used by default; original recognizable badges are preferred.
7. The community product must prioritize privacy, safety, and documented vetting.
8. Accuracy and copyright safety take priority over publishing speed.
